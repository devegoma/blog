# 記事・タグのデータ管理仕様（Issue #14）

更新日: 2026-11-01

[基本要件](../requirements.md) と、このチャットで確定した記事パス・タグ重複の扱いを、[親Issue #14](https://github.com/devegoma/blog/issues/14) と子Issue #19・#20・#21 の仕様へ具体化する。過去の記録にある記事内の固定名指定、1フォルダ1記事、`index.mdx` 固定、下書きの仮URLは採用しない。

## 基本要件と担当

| ---------------------------- | ------------------------------------------------------------ | ------------------------------------------- |

| 記事の URL と日付            | 相対パスによるURL、日付の形式と日本時間による範囲検証        | 形式・読み込みは #19、検証は #21            |

## 記事ファイルとURL（#19）

- 記事は `src/content/posts/` 内の `.mdx` ファイルとする。直下と任意の深さのサブフォルダを読み込む。`.md` は記事として読み込まない。
- 記事パスは、このディレクトリからの相対パスの末尾 `.mdx` を除き、区切りを `/` に統一した文字列とする。記事のIDにも同じ値を使う。
- フォルダ名と拡張子を除いたファイル名は、それぞれ `^[a-z0-9]+(?:-[a-z0-9]+)*$` に一致する。大文字、日本語、空白、アンダースコア、先頭・末尾や連続するハイフンは許可しない。公開・下書きで同じ規則を使う。
- 記事URLは `/posts/<記事パス>/`。パスの階層を保持し、`index` を省略しない。同じフォルダに複数の記事を置け、異なるフォルダで同じファイル名も使える。
- 記事パスとURLを一対一に対応させる。別名の `slug` 指定や、名前を自動で小文字化する処理で別の記事を同一URLへまとめない。
- タイトルの変更ではURLを変えない。ファイル名の変更や移動ではURLが変わるため、公開後は記事のパスを維持する。

| ファイル            | 記事パス・ID    | URL                     |
| ------------------- | --------------- | ----------------------- |
| `automation.mdx`    | `automation`    | `/posts/automation/`    |
| `astro/routing.mdx` | `astro/routing` | `/posts/astro/routing/` |
| `tools/routing.mdx` | `tools/routing` | `/posts/tools/routing/` |
| `astro/index.mdx`   | `astro/index`   | `/posts/astro/index/`   |

## 記事の入力項目（#19）

| 項目          | 入力                          | 公開記事                       | 下書き・省略時                                       |
| ------------- | ----------------------------- | ------------------------------ | ---------------------------------------------------- |
| `title`       | 空白だけではない文字列        | 必須                           | 必須                                                 |
| `date`        | `YYYY-MM-DD` の実在する年月日 | 必須。日本時間のビルド日以前   | 任意。入力時は形式と日付の実在性を検証               |
| `updated`     | `YYYY-MM-DD` の実在する年月日 | 任意。公開日以降、ビルド日以前 | 任意。入力時は形式と日付の実在性を検証               |
| `tags`        | タグの固定名の配列            | 任意                           | 省略時は空配列。参照検証・重複除去は公開・下書き共通 |
| `description` | 文字列                        | 任意                           | 任意。説明文未指定でも記事を保存・公開できる         |
| `draft`       | 真偽値                        | 明示的な `false` で公開対象    | `true` または省略で下書き                            |
| `slug`        | 入力禁止                      | ファイルパスを使う             | ファイルパスを使う                                   |

共通の読み込みで項目の型・既定値を揃える。入力元のファイルパスとMDX本文を保持し、検証エラーの表示と本文からの概要生成に利用できるようにする。記事パス・URLはファイル配置から導出する値であり、frontmatterへ重複入力しない。

`minutes`（読了時間）と `image`（一覧用サムネイル）は既存実装の任意の追加項目として扱う。公開に必要な項目へ追加しない。現在の実装では `minutes` は正の整数、`image` は `/images/` で始まる文字列。読了時間の算定方法と画像未指定時の表示は、基本要件から新たに確定した仕様とはせず、画面側の担当で扱う。本文内画像・一覧用画像・SNS共通画像を混同しない。

## タグの定義と参照（#20）

- 分類はタグだけとし、固定の記事種別・カテゴリを追加しない。
- 表示名とURL用固定名を一か所で管理する。既存の定義場所は `src/data/tags.ts`。
- 固定名は `^[a-z0-9]+(?:-[a-z0-9]+)*$` とし、タグURLは `/tags/<固定名>/`。表示名には日本語や `C++` を使える。
- 記事は表示名ではなく固定名を参照する。表示名だけを変えた場合は、参照する過去記事にも新しい表示名を使い、記事側の書き換えやタグURLの変更を不要にする。
- 複数タグ、タグなし、省略時の空配列を許可する。同じ記事内の同じ固定名は最初の指定順を保って重複を除去する。例: `[astro, typescript, astro]` → `[astro, typescript]`。
- 未定義の固定名への参照、定義内の固定名の重複、固定名の形式違反を検証エラーにする。記事内の重複除去によって、未定義の参照を検証しなくなることはない。
- 検証は下書きの入力済みタグにも適用する。タグ定義の重複は、後の定義で上書きされる前に検出する必要がある。
- 公開記事が1件以上あるタグだけをタグ一覧・タグページの対象とする選別は #22、画面の生成は #16 側で行う。#20 はその判定に使える定義と参照を渡す。

## 日付・入力検証・共通の並び順（#21）

公開日と更新日は執筆者が記事ファイルで管理する年月日であり、ファイルの更新時刻やGitの履歴で置き換えない。更新日の変更要否は執筆者が判断する。予約公開は設けない。

| 条件                                      | 公開記事 | 下書き |
| ----------------------------------------- | -------- | ------ |
| タイトル未入力・空白のみ                  | エラー   | エラー |
| 公開日未入力                              | エラー   | 許可   |
| 入力済み日付の形式違反・実在しない年月日  | エラー   | エラー |
| 公開日が日本時間のビルド日より未来        | エラー   | 許可   |
| 更新日が公開日より前                      | エラー   | 許可   |
| 更新日が日本時間のビルド日より未来        | エラー   | 許可   |
| 不正な記事パス・`slug` 指定・項目の型違反 | エラー   | エラー |
| 未定義タグの参照                          | エラー   | エラー |

公開記事の更新日は、公開日当日とビルド日当日を許可する。省略した更新日を自動補完せず、画面側では非表示にできるようにする。日本時間のビルド日を基準にし、CIのOSタイムゾーンに結果を依存させない。

検証エラーはビルドを失敗させ、対象ファイルと原因（対象項目または不正なパス）が分かるようにする。タグ定義のエラーなら定義ファイルと問題の固定名、記事からの参照エラーなら記事ファイルと参照先が分かるようにする。公開処理が失敗した成果物を配信しないことは #18 のCI/CDで保証する。

公開記事の共通の既定順は、公開日の降順、同日なら拡張子を除いた記事パス全体の昇順とする。ファイル名だけを比較しない。更新日は並び順に影響させない。表示順切り替えは画面側で扱い、RSSの既定順へ影響させない。公開日未入力の下書きを手元の画面でどう配置するかは、この公開記事の並び順の契約には含めない。

| 担当                          | #14から渡す内容と境界                                                                                                                                            |
| ----------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| #22 公開判定                  | 同じ記事型・`draft` の既定値・検証済みタグ参照を使い、公開対象を共通化する                                                                                       |

| #27 共通概要                  | 任意の説明文、本文、タイトルを渡す。説明文優先、未指定ならコード・表を除いた本文冒頭の通常の文章から最大120文字、抽出不可ならタイトルという処理は #27 で実装する |

現在の共通取得処理では、説明文省略時にタイトルを使っている。これは本文からの概要抽出が完了していることを意味しない。RSS・SNS共有へ接続するときに #27 の確定要件を満たす必要がある。

## 実装と検証で残る確認事項

- `src/data/tags.ts` の固定名の形式と、定義の重複を実際にどの検査で止めるかを確認し、異常系の証拠を #20 に記録する。型付きオブジェクトであることだけを、両方の検証の完了証拠にしない。
- #21 のうるう年・日本時間の日付境界・公開日/更新日とビルド日の等号境界・下書きから公開への制約切り替え・パス全体による既定順は、[入力検証と既定順の検証記録](../verification/issue-21.md) に方法・結果・利用側との接続と範囲を記録する。
- `minutes` の算定、画像未指定時の見た目、公開日がない下書きの画面上の順序は、#14の基本要件から追加決定しない。担当する画面・プレビューのIssueで必要時に具体化する。
- 仕様書の作成と実装・検証・本番公開の完了を区別し、対象コミットと検証結果で確認する。
