## 対象外と検証の境界

本番デプロイ、Cloudflareの設定変更、mainの保護、ドメイン・HTTPS、正式記事の執筆は行いません。GitHub上での実際のキュー制御と公開の受け入れ検証は #70 が担当します。隔離検証は、ワークフローのconcurrency設定に従ってキューを模擬し、実際の公開判定とシェルコマンドを呼び出します。GitHubのサービス自体を実行した検証とは区別します。

## 競合時の方針

公開ジョブ全体に固定の共通グループを使います。実行中の公開は中止しません。GitHub標準の待機枠は1件とし、さらに新しいジョブが待機すると以前の待機ジョブは置き換えられます。mainの照合は待機から実行に移った後に行うため、待機前の確認結果を使い回しません。[GitHub公式仕様（2026/11確認）](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency) に基づく方針です。

## 実装した公開経路

`.github/workflows/ci.yml` の公開ジョブ全体に、固定グループ `pages-blog-production` と `cancel-in-progress: false` を設定しました。ブランチ名、実行番号、ワークフロー名はグループに含めません。Checksは同じグループに入れず、検査そのものの並列実行は維持します。今後別の本番公開経路を追加する場合も同じグループを使う必要があります。

公開ジョブは、待機を終えてからチェックアウト、実行環境の準備、検査済み成果物の取得と照合を行います。続いて固定版Wrangler 4.135.0を `--version` で準備します。この準備にはCloudflare Secretsを渡しません。準備が失敗した場合も公開へ進みません。

次に `node scripts/check-latest-main.mjs` を実行します。このコマンドは `git ls-remote --exit-code origin refs/heads/main` でリモートmainのコミットを確認します。手元の `origin/main` や以前の照合結果は使いません。取得の制限時間は15秒です。対象の `GITHUB_SHA` と完全一致した場合だけ `GITHUB_OUTPUT` に `publish=true` を書き込みます。不一致、取得失敗、mainの欠落、不正な対象や応答は `publish=false` とします。

判定ステップの直後に、`steps.latest-main.outputs.publish == 'true'` を条件とする公開ステップを置きます。取得した同じ成果物を、#68で固定したWranglerコマンドへ渡します。再ビルドは行いません。mainの確認後にmain自体が更新される可能性はありますが、公開ジョブの共通グループは公開完了まで保持します。新しいジョブは先行の公開が完了してから改めてmainを照合します。実行順序の保証には依存しません。

## 判定ログ

標準出力とActionsの実行サマリーに `target`、`latest-main`、`decision`、`reason` を記録します。`decision` は `publish` または `skip` です。`reason` は次の意味です。

| reason             | 意味                                                           |
| ------------------ | -------------------------------------------------------------- |
| `latest-main`      | 対象コミットとリモートmainが一致しました。                     |
| `stale-commit`     | リモートmainは確認できましたが、対象コミットと一致しません。   |
| `main-unavailable` | mainの取得に失敗しました。mainの欠落や制限時間超過も含みます。 |
| `invalid-target`   | 対象コミットの形式が不正です。                                 |
| `invalid-response` | Gitの応答をmainのコミットとして解釈できません。                |

確認できないmainは `unknown` と表示します。Gitのエラー出力には認証情報付きURLが含まれる可能性があるため、そのままログへ転記しません。Cloudflare Secretsは引き続き公開ステップだけに渡します。

## 隔離検証の方法

`pnpm test:ci` に2つの検査を含めます。

- `scripts/check-ci-deployment.mjs`: #68の検査を拡張し、23シナリオでmain・develop・PR・手動起動・必須チェック失敗・改変・最新main不一致・取得失敗・Wrangler準備失敗を検証します。有効化後の実際の条件式をそのまま評価します。条件式をメモリ上で書き換える処理と、固定停止状態の4ケースは削除しました。
- `scripts/check-ci-order.mjs`: 実際のconcurrency設定に従う模擬キューを使い、別プロセスでワークフローのコマンドと最新main確認を実行します。ローカルのGitリモートを更新しながら、同時実行、待機中の更新、待機ジョブの置き換え、待機後の取得失敗の4ケースを検証します。さらに古いコミットを再実行し、公開処理が追加で呼ばれないことを確認します。

公開ステップのpnpmコマンドは、一時ディレクトリ内の記録用処理へ置き換えます。先行の公開処理を保持し、後続をキューへ入れた後にmainを更新してから解放します。開始・終了の記録から同時実行数が1件以下であることを確認します。古いコミットの再実行でも成果物の検査・照合を通し、その後の最新main確認でスキップするため、成果物の不整合だけで公開が止まった結果とは区別できます。

## 公開の有効化と承認

自動承認審査は、固定の `false` 条件を削除する変更を、本番Pages公開を有効化する永続的な変更と判定しました。Issue対応の実装・検証依頼だけでは明示承認にならないとして拒否されたため、停止条件を復元しました。

2026-11-16に利用者から「有効化を承認する」と回答を受け、公開ジョブ条件の先頭にある `false &&` を削除しました。mainへのpush、Checks成功、同時実行制御、成果物照合、最新mainとの一致はすべて維持しています。この構成がmainに反映されると本番自動公開が動きます。今回の作業ではmainへの反映や実際の本番公開は行っていません。
